# Dense Notes

The retrieval service accepts a natural language question and returns the passages most likely to contain the answer. It embeds the question with the same model used at ingest time, because vectors from different models are not comparable and mixing them produces results that look plausible but are meaningless. The search then compares that vector against every stored vector and returns the closest matches ranked by distance. Callers receive the passage text, its source metadata, and the distance score so they can decide whether a match is strong enough to act on.

Ranking quality depends on more than the embedding model. Chunk boundaries matter because a passage that begins halfway through an explanation carries less meaning than one that starts at a section heading. Overlap matters because an answer sentence that straddles a boundary would otherwise be split across two passages and match neither well. Metadata matters because filtering by source or freshness removes candidates that would otherwise crowd out better matches. None of these are visible in the embedding model's benchmark score.

Evaluation should come before optimisation. A retrieval precision figure measured against real questions tells you whether the pipeline meets its target, and which stage is responsible when it does not. Without that figure, changing the chunk size or swapping the model is guesswork dressed up as engineering. Teams that tune parameters before measuring usually improve the number they happened to look at rather than the one that mattered to anybody using the system.

Token limits are the constraint that bites first and complains least. Every embedding model accepts a fixed number of tokens and silently discards whatever arrives after that point. No exception is raised and no warning appears in the logs, so a pipeline that feeds oversized passages will index only their opening sections while appearing to work normally. The stored text remains complete, which makes the failure harder to spot, because a retrieved passage looks intact even when its tail never influenced the vector.

Technical prose tokenises far more heavily than ordinary writing. Identifiers written in camel case are split into several pieces, URLs fragment at every separator, and internal acronyms that never appeared in the training data are broken down character by character. A rule of thumb that assumes four characters to the token will therefore underestimate the real count substantially on exactly the documents an engineering knowledge base contains. Measuring with the model's own tokenizer avoids the guesswork entirely.

Persistence deserves more attention than it usually receives. A vector database running in a container writes to a path inside that container, and unless the path is mounted to a volume the data disappears the moment the container is replaced. The failure is quiet because the pipeline simply rebuilds the index on the next run, which looks like correct behaviour until somebody expects the data to survive a deployment. Verifying persistence means destroying the container deliberately and checking the count afterwards.

Identifiers for stored passages must be stable and unique. Stability means the same passage produces the same identifier on every run, so re-ingesting a document replaces its existing entries rather than creating duplicates alongside them. Uniqueness means no two passages from different documents collide, which rules out using the position within a document on its own, since every document begins counting from zero. Combining the source path with the position satisfies both requirements without needing a lookup table.

Citations are the mechanism that makes grounding verifiable. An answer that names its source can be checked in seconds by anybody who doubts it, while an answer without one has to be trusted or researched from scratch, which defeats the purpose of the tool. The metadata that supports a citation has to be captured when the file is first read and carried through every subsequent stage, because once a passage has been reduced to a vector there is no way to recover where it came from.

Failure handling determines whether a pipeline is usable at scale. A single unreadable file in a directory of hundreds should produce a logged warning and be skipped, not halt the run and leave the remaining documents unprocessed. The warning needs to name the file and the underlying reason, because an operator reading the log afterwards has no other way to tell whether the problem was a permissions error, an unexpected encoding, or a file that was never meant to be ingested at all.
